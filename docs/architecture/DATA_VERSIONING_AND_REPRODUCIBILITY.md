This document defines how future engineering inputs, calculations, and reports will remain traceable, deterministic, edition-aware, testable, and historically reproducible. It specifies version identities, canonical normalization, fingerprints, immutable snapshots, staleness, and migration policy without implementing serialization, hashing, persistence, equations, or calculations. Stage 1.3A spatial/action objects, Stage 1.3B exact nominal section geometry, and Stage 1.3C1 component placement/extrusion objects are in-memory framework-independent contracts only; no public document, DTO, API, database, or fingerprint representation is introduced.

Reproducibility means the system can identify the exact engineering inputs and approved source/data/software context used for a calculation attempt and can distinguish that historical context from a later recalculation. It does not mean an obsolete result is current or still approved.

## Version vector

Each calculation snapshot must record the independent version dimensions it actually relies upon. No single application version may stand in for all of them.

| Version dimension | What it controls | Required behavior |
|---|---|---|
| Project schema version | Structure and semantics of `EngineeringProjectDocument`. | Read before interpretation; migration must be explicit and traceable. Current value is `0.1.0-draft`. |
| Calculation-engine version | Executable orchestration and deterministic calculation implementation. | Recorded for every calculation attempt. Stage 1.3B value is `Not implemented`. |
| Engineering-rule-set version | Approved mapping of engineering sources, applicability, assumptions, limit states, and result behavior. | Recorded independently of engine version. Stage 1.3B value is `Not implemented`. |
| Standard edition | Exact edition of each governing standard. | Required for source-dependent results; current registered basis is ASCE/SEI 74-23. |
| Errata version | Verified correction/errata set applied to the standard edition. | Must identify a verified set or `verification pending`; a pending set cannot support an unqualified source-dependent success. |
| Material-data version | Controlled material property dataset and qualification state. | Required when material data affects applicability or results. |
| Section-data version | Controlled section geometry/property dataset. | Required when section data affects geometry or results. |
| Manufacturer-data version | Controlled manufacturer-specific data and provenance/qualification state. | Required when manufacturer data is relied upon. |
| Capability/approval version | Supported-slice, applicability, verification, and engineer-approval record. | Required to show that an implemented method was qualified for the requested condition. |
| Report definition version | Summary/Detailed report structure, labels, and presentation rules. | Recorded by report snapshots; it may not alter engineering results. |

Material, section, and manufacturer data may have multiple independently versioned sources. A snapshot records each source identifier/version used, not merely a generic current-data label.

Exact version syntax and compatibility ranges are **Pending Architecture Decisions**. Exact qualification workflows for material and manufacturer data are **Pending Engineering Decisions**.

## Engineering document and ownership separation

**Provisional architecture:** `ProjectRecord` is an ownership/lifecycle/security envelope, while `EngineeringProjectDocument` contains versioned calculation inputs. The latter can be normalized for calculation without importing account, organization, role, entitlement, billing, retention, or access-control state.

**Provisional — PRV-015:** a project schema should support one or more joint assemblies, even if the MVP exposes one. The engineering document retains stable entity references needed to reconstruct topology and result traceability.

Ownership changes do not alter the engineering content and must not change the engineering fingerprint. Authorization remains required to access or calculate the project; fingerprint exclusion is not an authorization bypass.

## Canonical input normalization

Before a calculation can be fingerprinted, its engineering input is converted to one canonical, versioned representation. The normalization contract must be documented, deterministic, and itself version-controlled.

Conceptually, normalization must:

1. validate the declared project schema version before interpreting fields;
2. preserve all physical topology, including component-scoped physical section elements, material regions, element-to-region references, topology source/family, material orientation rules, exact nominal section dimensions/geometry/idealization, physical-element geometry mappings, deferred features, nominal voids, Stage 1.3C1 participant identity, authoritative resolved global placement, longitudinal extent, section offset, physical/deferred/void extrusion descriptors, physical boundary-plane identity/normals, member START/END and connected-end meaning, and the member/component identities needed for relationships, interfaces, bolt stacks, shared regions, load paths, combinations, actions, symbolic frame references, resolved-frame provenance, and reference points;
3. make engineering defaults explicit rather than deriving them from UI state or omission;
4. preserve signed quantities, physical dimensions, coordinate-frame meaning, explicit frame-construction provenance, connected-end identity, and reference-point eccentricities;
5. represent semantically unordered collections in a documented stable order without changing ordered physical structures such as bolt stacks;
6. reject duplicate/ambiguous identifiers, unsupported values, non-finite values, or lossy unit conversions;
7. resolve engineering data references to the exact controlled versions used; and
8. exclude presentation-only, security, ownership, and lifecycle metadata from the engineering calculation content.

The exact internal canonical unit system and numeric serialization/precision rules are **Pending Engineering and Architecture Decisions**. Until approved and independently verified, unit-dependent fingerprints and cross-unit equivalence are not qualified.

Normalization must never fill a missing engineering input with a display default, invent a load path, drop an unsupported force component, apply an additional load factor, infer structural credit from geometry, or convert unresolved source data into an approved value.

## Calculation fingerprint

**Provisional architecture:** generate a SHA-256 calculation fingerprint from canonical serialization of normalized engineering inputs plus the calculation-affecting version/data context. The fingerprint algorithm, serialization profile, and inclusion rules must be versioned and tested before use.

### Included in the engineering fingerprint

- canonical joint topology, physical section elements, material regions, material-axis families/orientation rules, and calculation-relevant entity relationships;
- engineering geometry, explicit units/dimensions, materials, sections, and manufacturer references/data used;
- interfaces, bolt groups, bolt stacks, reinforcement, load paths, and shared regions;
- load combinations and signed member-end actions, including frames and reference points;
- future resolved origins and basis axes, explicit local-z reference provenance, proper-transform operation order, action-direction identity, and explicit reference-point shift provenance when those contracts are serialized under a later approved schema;
- future canonical section dimensions, local-y/local-z datum and bounds, exact profile
  representation/idealization, ordered physical-element mappings, deferred features,
  nominal voids, and topology association when Stage 1.3B contracts are serialized
  under a later approved schema;
- future Stage 1.3C1 placed component identity/kind, one authoritative global frame,
  explicit local-x extent, explicit y/z section offset, local/global point-mapping
  meaning, boundary identities/outward normals, START/END/connected-end semantics, and
  exact physical/deferred/void analytic extrusion descriptors when serialized under a
  later approved schema;
- calculation-relevant project settings and explicit approved assumptions;
- project schema/normalization contract version;
- calculation-engine and engineering-rule-set versions;
- governing standard editions and verified errata identifiers;
- material-, section-, manufacturer-, and capability/approval-data versions; and
- any other input that can change applicability, demand, resistance, utilization, status, warnings, or intermediate values.

### Excluded from the engineering fingerprint

- account ID, organization ID, owners, collaborators, roles, and entitlement/billing state;
- project-access, retention, audit, and lifecycle metadata;
- user names, email addresses, session identity, and provider identifiers;
- mutable titles/notes that have no engineering meaning;
- camera, zoom, selection, panel, color, visibility, and other display-only state;
- renderer meshes, annulus tessellation vertices/settings, drawing linework, and other
  derived section-display approximations;
- report page layout and formatting that cannot affect engineering values; and
- timestamps, storage keys, and generated artifact locations.

Engineering-relevant notes or explicit assumptions cannot be excluded merely because they are stored as text. Exact treatment of stable engineering entity identifiers and non-engineering metadata is a **Pending Architecture Decision**.

A fingerprint is an integrity/reproducibility identifier, not a digital signature, authorization token, proof of engineering approval, or substitute for snapshot provenance.

## Immutable calculation snapshots

A `CalculationSnapshot` freezes one calculation attempt and contains, at minimum:

- immutable snapshot identity and creation metadata;
- normalized canonical engineering inputs or an immutable, content-addressed reference to them;
- calculation fingerprint and fingerprint-contract version;
- the complete version vector and source/data provenance;
- capability, applicability, and engineer-approval context;
- structured results at required interface, component, shared-region, and whole-joint levels;
- explicit warnings, assumptions, unsupported/incomplete conditions, and execution diagnostics; and
- traceability to the originating engineering document revision without depending on mutable ownership data.

Snapshots are append-only records. Editing a project, changing a rule/data version, resolving errata, or fixing software creates a new calculation attempt/snapshot; it does not rewrite an old snapshot. A failed, incomplete, unsupported, or review-required attempt may be retained accurately, but it may not be represented as a successful calculation.

No calculation snapshot or calculation fingerprint is generated in Stage 1.3C1
because no calculation engine or rule set exists. Implemented spatial transformations,
nominal section factories, and placement/extrusion builders do not authorize a
snapshot, fingerprint, result, persisted frame registry, or persisted component
placement.

## Immutable report snapshots

A `ReportSnapshot` freezes the report presentation derived from one immutable calculation snapshot. It records the referenced calculation snapshot/fingerprint, report definition version, selected Summary or Detailed presentation, controlled labels/notes, creation context, and future artifact-integrity metadata.

Summary and Detailed reports use the same immutable structured result data. A report snapshot cannot:

- recalculate or reinterpret a check;
- change applicability or result status;
- omit a required unsupported/incomplete/review/stale disclosure;
- turn absent capacity fields into zero or `PASS`; or
- mutate the calculation snapshot it references.

If a report is regenerated under a new report definition without recalculation, it becomes a new report snapshot that still references the original calculation snapshot. Report signing or sealing is a **Pending Engineering Decision** requiring business and legal approval as well.

## Stale-result detection

A result is current only when the active normalized engineering input fingerprint and all calculation-affecting versions match the calculation snapshot under the approved compatibility policy.

Changes to any included input or calculation-affecting version make the prior result stale for the active document, including:

- engineering geometry, topology, material, section, bolt stack, load path, shared region, action, frame, reference point, or approved assumption;
- calculation engine or rule set;
- standard edition or errata set;
- material, section, manufacturer, capability, applicability, or approval data; or
- normalization/fingerprint behavior that changes engineering meaning.

Ownership, entitlement, camera, selection, and other explicitly excluded metadata do not make the engineering result stale, although they may change whether it can be accessed or used.

The active project must show `STALE RESULTS`; warnings alone are insufficient. The immutable historical snapshot retains the status originally produced in its historical context and is not edited to say stale. Exact compatibility rules for changes claimed to be non-affecting are **Pending Engineering and Architecture Decisions**; absence of an approved rule fails closed as stale or unsupported.

## Historical viewing versus recalculation

Historical viewing presents the original immutable input, version vector, provenance, results, and report association with a clear historical/not-current label. It must not silently substitute current material data, errata, engine behavior, or report interpretations.

Recalculation is an explicit operation that:

1. checks current authorization and entitlement outside the calculation core;
2. migrates or validates a copy of the engineering document under approved policy;
3. resolves the deliberately selected current version/data context;
4. creates a new normalized input and fingerprint; and
5. records a new immutable calculation snapshot.

The old snapshot remains available according to the future access and retention policy. A recalculation may produce a different result; the system preserves both contexts and does not overwrite history.

## Migration policy

Project-document migration changes data representation; it does not automatically approve new engineering meaning.

Stage 1.2 performs an internal source/test migration from preliminary
`FRPMaterialAxes` to `FRPComponentOrientation` plus regional orientation. No persisted
user-document migration is supplied because no persistence or public serialization
contract exists. A future schema migrator must not infer regional CW/TT from a legacy
component-wide CW for multi-plane or cylindrical sections.

Stage 1.3A likewise adds only in-memory spatial and action-transformation contracts. It
performs no project-schema migration and does not infer member placement or resolve a
symbolic frame. A later spatial migration must not silently choose a local-z reference,
repair a reflected/skewed basis, reverse member x for a connected end, infer a moment
reference point, or apply an automatic reference-point shift.

Stage 1.3B adds only in-memory exact nominal standard-section contracts. It performs no
project-schema migration and does not attach geometry to an assembly entity. A later
geometry migration must not infer dimensions, change the outside-bounds datum, assign
deferred junction/corner geometry to material, invent local-x extrusion or placement,
tessellate an analytic annulus into canonical data, or treat a drawable profile as a
connection target or calculated section property.

Stage 1.3C1 likewise adds only in-memory component placement and analytic extrusion
contracts. It performs no project-schema migration and adds no placement registry to
`JointAssembly`. A later placement migration must not infer a section offset or
connector extent, silently choose a local-z reference, reverse member x based on
connected end, repair an improper/reflected frame, add a second roll or mirror state,
merge separate physical elements, thicken deferred line surfaces, replace analytic
annular geometry with a mesh, reinterpret an end plane as a connection face, or infer
holes, bolts, force points, eccentricity, or section properties.

Stage 1.3C2A adds only in-memory surface-patch and explicit bounded support-surface
contracts. A later migration must not derive identity from renderer triangles, merge
separate element-level patches, reverse signed normals from camera orientation,
target deferred/internal patches, infer a support plane from support kind, or create
an interface target or connection zone.

- Every stored document declares its schema version.
- Migrations are explicit, deterministic, directional, tested transformations with source and target versions.
- The original document/snapshot remains immutable and recoverable according to retention policy.
- A migration records its tool/version, time, diagnostics, fields changed, defaults applied, and unresolved/lossy items.
- Engineering defaults may be introduced only when their meaning is approved and visible; otherwise user input or engineering review is required.
- Unknown future versions, missing migrators, ambiguity, data loss, or unsupported engineering semantics fail closed as unreadable for recalculation, `INCOMPLETE INPUT`, `ENGINEERING REVIEW REQUIRED`, or `CALCULATION NOT SUPPORTED`, as appropriate.
- Migration never upgrades a historical result, transfers `PASS` to changed inputs, or creates capacity data.
- Recalculation after migration produces a new snapshot/fingerprint; it does not attach new results to the old snapshot.

Snapshot/result schemas require their own compatibility policy. A historical viewer may preserve/render an older snapshot without asserting that the current engine can recalculate it.

## Fail-closed reproducibility rules

- Missing or unrecognized project, engine, rule-set, source, errata, or engineering-data versions cannot be treated as current defaults.
- `verification pending` errata remains explicit and cannot be silently upgraded.
- A fingerprint mismatch is never ignored or repaired by presentation code.
- Missing canonical inputs, capacity fields, or provenance are not converted to zero, `PASS`, or `FAIL`.
- Placeholder calculations and migrations may never emit engineering `PASS` or `FAIL`.
- Warnings cannot replace `STALE RESULTS`, `INCOMPLETE INPUT`, `CALCULATION NOT SUPPORTED`, `ENGINEERING REVIEW REQUIRED`, or another required result state.
- Historical accessibility does not mean a result is current, commercially validated, or authorized for a new design use.
